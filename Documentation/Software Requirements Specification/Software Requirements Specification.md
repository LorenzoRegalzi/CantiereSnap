## 1. Introduction

### 1.1 Purpose

This document defines the functional and non-functional requirements for CantiereSnap, an AI-augmented, serverless cloud platform designed for micro-enterprise job management in the Italian construction sector. It serves as the contractual baseline between development and evaluation: every feature described here will be implemented, tested, and validated against the acceptance criteria listed.

### 1.2 Scope

CantiereSnap targets solo tradespeople (*artigiani*) who operate micro-enterprises with fewer than 10 employees. The platform covers the full job lifecycle: quoting, job tracking, photo documentation, material cost logging, electronic invoicing compliant with Italy's *Sistema di Interscambio* (SDI), and business analytics. The system is delivered as a Progressive Web Application (PWA) backed by a fully serverless AWS architecture, with AI capabilities powered by the Anthropic Claude API.

### 1.3 Target Users

The primary user is the independent Italian tradesperson: a plumber, electrician, painter, or renovation contractor running a one-person or small-crew operation. This user typically manages jobs using paper notebooks, WhatsApp photo threads, and manual spreadsheets. They need a tool that works on a phone at a jobsite, not a desktop ERP suite designed for a project manager with a dual monitor setup.

### 1.4 Definitions and Acronyms

| Term | Definition |
|------|-----------|
| Artigiano | Italian term for independent tradesperson or craftsperson |
| FatturaPA | The XML-based electronic invoice format mandated by Italian tax law for all B2B and B2G transactions |
| SDI | Sistema di Interscambio — the Italian government's electronic invoice exchange system managed by Agenzia delle Entrate |
| Regime Forfettario | A simplified Italian tax regime for small businesses and freelancers with annual revenue below €85,000 |
| PWA | Progressive Web Application — a web app installable on mobile devices with offline capabilities |
| LLM | Large Language Model — the AI model (Claude API) used for natural-language processing tasks |
| Cold Start | The initial latency when a serverless function is invoked after a period of inactivity |
| Presigned URL | A time-limited, authenticated URL generated by AWS S3 to allow direct file upload from the client |

## 2. User Stories

All user stories are written from the perspective of the tradesperson, the sole user role in CantiereSnap v1.0. Stories are grouped by module and follow the format: As a [role], I want to [action], so that [benefit]. Each story includes measurable acceptance criteria that map directly to the functional requirements in Section 3.

### 2.1 Authentication (AUTH)

**US-AUTH-001:** As a tradesperson, I want to register with my email and a password, so that I can access my own data securely from any device.

**Acceptance Criteria:**

- The registration form requires a valid email address and a password of at least 8 characters.
- The system sends a verification email upon registration.
- The tradesperson cannot access protected features until email verification is complete.
- After verification, login returns a JWT token used for all subsequent API calls.

**US-AUTH-002:** As a tradesperson, I want to stay logged in across sessions, so that I don't have to re-enter credentials every time I open the app on my phone.

**Acceptance Criteria:**

- The JWT refresh token keeps the session active for at least 30 days.
- If the refresh token expires, the tradesperson is redirected to the login screen.

### 2.2 Job Pipeline (JOB)

**US-JOB-001:** As a tradesperson, I want to create a new job with client details, a description, and a target date, so that I have a central record for every piece of work I take on.

**Acceptance Criteria:**

- The job creation form captures: client name, client contact info, job description, address, and target completion date.
- The new job appears in the pipeline with status "Quote" by default.
- Each job is assigned a unique, sequential job ID visible to the tradesperson.

**US-JOB-002:** As a tradesperson, I want to move a job through defined stages (Quote → Accepted → In Progress → Completed → Invoiced), so that I always know where each job stands.

**Acceptance Criteria:**

- Status transitions are sequential — a job cannot skip stages.
- Each transition records a timestamp visible in the job detail view.
- The Kanban board updates in real time when a job status changes.

**US-JOB-003:** As a tradesperson, I want to filter and search jobs by status, client name, or date range, so that I can quickly find specific jobs.

**Acceptance Criteria:**

- The pipeline view supports filtering by status (single or multiple).
- A search bar matches against client name and job description.
- Filters and search can be combined.

### 2.3 AI Quote Generation (QUOTE)

**US-QUOTE-001:** As a tradesperson, I want to describe a job in my own words and receive a structured, itemised PDF quote, so that I can send a professional document to the client without manually formatting it.

**Acceptance Criteria:**

- The system accepts a natural-language description of at least 500 characters.
- The AI generates itemised line items with descriptions, quantities, unit prices, and a total.
- The output is a downloadable PDF with CantiereSnap branding.
- Generation completes within 15 seconds under normal conditions.

**US-QUOTE-002:** As a tradesperson, I want to review and edit the AI-generated quote items before finalising, so that I can correct prices or add missing work.

**Acceptance Criteria:**

- Each generated line item is individually editable (description, quantity, unit price).
- The tradesperson can add or remove line items manually.
- The total recalculates automatically after edits.
- Once approved, the final version is saved as the quote of record.

**US-QUOTE-003:** As a tradesperson, I want to send the finalised PDF quote to the client via email directly from the app, so that I don't have to download and forward it manually.

**Acceptance Criteria:**

- The send action requires only the client's email address (pre-filled from job data).
- The email includes the PDF as an attachment with a professional template.
- The system records that the quote was sent, with a timestamp.

### 2.4 Photo Documentation (PHOTO)

**US-PHOTO-001:** As a tradesperson, I want to upload before and after photos for each job, so that I have visual evidence of the work performed in case of disputes.

**Acceptance Criteria:**

- Photos can be uploaded directly from the device camera or gallery.
- Each photo is tagged as "Before" or "After."
- Photos are stored in a per-job gallery accessible from the job detail view.
- The system supports JPEG and PNG formats up to 10 MB per image.

**US-PHOTO-002:** As a tradesperson, I want each uploaded photo to have an AI-generated technical description, so that the documentation is useful even without visual context (e.g., in a legal dispute summary).

**Acceptance Criteria:**

- The AI generates a description within 10 seconds of upload.
- The description identifies materials, tools, and work performed where visible.
- The tradesperson can edit or override the generated description.

### 2.5 OCR Material Logging (OCR)

**US-OCR-001:** As a tradesperson, I want to photograph a receipt or handwritten note and have the material costs extracted automatically, so that I don't have to type them in manually.

**Acceptance Criteria:**

- The system accepts a photo of a receipt, invoice, or handwritten cost note.
- AWS Textract extracts text from the image and the system parses it into structured entries: item name, quantity, and cost.
- Extracted entries are linked to the current job.
- The tradesperson can review and correct extracted data before saving.

### 2.6 Electronic Invoicing (INV)

**US-INV-001:** As a tradesperson, I want to generate a *FatturaPA*-compliant electronic invoice from a completed job, so that I meet the SDI requirement without needing separate invoicing software.

**Acceptance Criteria:**

- The invoice form pre-fills client data and line items from the job and quote records.
- The system generates a valid *FatturaPA* XML file conforming to SDI schema v1.2.
- The generated XML is downloadable and can be submitted to the SDI through any accredited channel.
- Invoice data includes: seller fiscal data, buyer fiscal data, line items, VAT calculation, and payment terms.

**US-INV-002:** As a tradesperson, I want to track the status of each invoice (Sent, Paid, Overdue), so that I know which clients still owe me money.

**Acceptance Criteria:**

- The invoice status is updated manually by the tradesperson or automatically via overdue rules.
- Overdue invoices are highlighted in the dashboard and trigger reminder notifications.
- The job pipeline reflects the invoice status (a job reaches "Invoiced" only after an invoice is generated).

### 2.7 Dashboard and Analytics (DASH)

**US-DASH-001:** As a tradesperson, I want a dashboard showing my monthly revenue, job completion rates, average quote-to-invoice time, and material costs, so that I can understand my business performance at a glance.

**Acceptance Criteria:**

- The dashboard loads within 3 seconds.
- Revenue is displayed as a monthly bar or line chart.
- Job completion rate shows the ratio of completed jobs to total jobs in the period.
- Quote-to-invoice time is averaged across all completed jobs.
- Material costs are broken down by job or by period.
- A date range filter allows selecting custom time windows.

### 2.8 Notifications (NOTIFY)

**US-NOTIFY-001:** As a tradesperson, I want to receive automatic email reminders when an invoice is approaching its due date or is overdue, so that I can follow up with clients without tracking dates manually.

**Acceptance Criteria:**

- The system sends an email reminder 7 days before the invoice due date.
- The system sends an overdue alert on the day after the due date.
- Reminder emails include the invoice number, client name, amount, and due date.

**US-NOTIFY-002:** As a tradesperson, I want to send SMS appointment reminders to clients, so that they remember scheduled job dates.

**Acceptance Criteria:**

- The tradesperson can schedule an SMS reminder linked to a job's target date.
- The SMS is sent to the client's phone number stored in the job record.
- SMS content includes the job date, time, and a brief description.

## 4. Non-Functional Requirements

Non-functional requirements define the quality attributes of the system. They are particularly important for CantiereSnap because the serverless architecture introduces specific trade-offs around latency, cost, and availability that differ from traditional deployments.

### 4.1 Performance

| ID | Requirement | Priority |
|----|-------------|----------|
| `NFR-PERF-001` | API responses for CRUD operations (jobs, clients, invoices) shall complete within 500ms at the 95th percentile, excluding cold starts. | **Must** |
| `NFR-PERF-002` | Lambda cold start latency shall not exceed 3 seconds for any function. | Should |
| `NFR-PERF-003` | AI quote generation (Claude API call + PDF rendering) shall complete within 15 seconds end-to-end. | **Must** |
| `NFR-PERF-004` | Photo upload via presigned URL shall support files up to 10 MB without timeout. | **Must** |
| `NFR-PERF-005` | The dashboard shall load all metrics within 3 seconds on a 4G mobile connection. | Should |

### 4.2 Scalability

| ID | Requirement | Priority |
|----|-------------|----------|
| `NFR-SCALE-001` | The system shall support up to 1,000 concurrent users without manual infrastructure changes, leveraging DynamoDB on-demand capacity and Lambda auto-scaling. | Should |
| `NFR-SCALE-002` | S3 storage shall scale automatically with no pre-provisioned capacity, using lifecycle policies to transition infrequently accessed photos to S3 Infrequent Access after 90 days. | **Must** |

### 4.3 Security

| ID | Requirement | Priority |
|----|-------------|----------|
| `NFR-SEC-001` | All API communication shall use HTTPS (TLS 1.2 or higher). | **Must** |
| `NFR-SEC-002` | All API endpoints shall be protected by a Cognito JWT authoriser. No endpoint shall be publicly accessible without authentication. | **Must** |
| `NFR-SEC-003` | S3 objects shall be private by default. Access is granted only via time-limited presigned URLs (maximum validity: 15 minutes). | **Must** |
| `NFR-SEC-004` | User data in DynamoDB shall be logically isolated by user ID in the partition key. No user can access another user's records. | **Must** |
| `NFR-SEC-005` | API Gateway shall enforce request throttling at 100 requests per second per user to prevent abuse. | Should |

### 4.4 Availability and Reliability

| ID | Requirement | Priority |
|----|-------------|----------|
| `NFR-AVAIL-001` | The system shall target 99.9% uptime, consistent with AWS Lambda and DynamoDB SLAs. | Should |
| `NFR-AVAIL-002` | The system shall handle Claude API unavailability gracefully by displaying a user-friendly error and allowing manual quote creation as a fallback. | **Must** |
| `NFR-AVAIL-003` | EventBridge-triggered Lambda functions shall retry failed executions up to 2 times with exponential backoff. | Should |

### 4.5 Cost

| ID | Requirement | Priority |
|----|-------------|----------|
| `NFR-COST-001` | The infrastructure shall operate within the AWS Free Tier for the first 50 active users (leveraging Cognito's 50K free MAUs, DynamoDB on-demand, and Lambda's 1M free requests/month). | **Must** |

| `NFR-COST-003` | S3 lifecycle policies shall move objects older than 90 days to S3 Infrequent Access and delete objects older than 365 days (configurable). | Should |

## 5. System Constraints

### 5.1 Technical Constraints

The backend is fully serverless on AWS. No EC2 instances, no self-managed containers in the MVP. Lambda functions are the sole compute layer, with API Gateway as the entry point. DynamoDB uses a single-table design — all entities (jobs, clients, quotes, invoices, photos) share one table with carefully designed partition and sort keys.

The frontend is a static Next.js PWA deployed to S3 and served via CloudFront. Server-side rendering is not used; all API calls are client-initiated.

### 5.2 Regulatory Constraints

Electronic invoices must conform to the *FatturaPA* XML schema mandated by the Agenzia delle Entrate. The system generates the XML file but does not transmit it directly to the SDI — the tradesperson uses an accredited intermediary (*intermediario accreditato*) for transmission. This is a deliberate scope boundary: SDI transmission requires formal accreditation that is outside the scope of a capstone project.

### 5.3 Budget Constraints

The project operates on a zero-budget basis. All AWS services must fall within the Free Tier or have negligible cost at the expected usage level (fewer than 50 users during validation). The only paid external service is the Anthropic Claude API, which is budgeted at a maximum of $50 for the entire development and testing phase.

## 6. Assumptions and Dependencies

### 6.1 Assumptions

The tradesperson has a smartphone with a camera and a mobile data connection (3G or better). They are comfortable typing short descriptions in Italian but are not expected to use technical jargon or structured input formats. They handle 5–30 active jobs at any given time. They already have their fiscal data (Partita IVA, codice fiscale, regime fiscale) available for invoice configuration.

### 6.2 Dependencies

| Dependency | Provider | Risk if Unavailable |
|-----------|----------|---------------------|
| Claude API | Anthropic | Quote generation and photo descriptions are disabled. Manual entry remains available as fallback. |
| AWS Lambda | Amazon Web Services | Entire backend is non-functional. Mitigated by AWS's 99.95% SLA. |
| AWS Textract | Amazon Web Services | OCR feature is disabled. Tradesperson enters material costs manually. |
| AWS SES / SNS | Amazon Web Services | Email and SMS notifications fail. Core job management remains operational. |
| FatturaPA Schema | Agenzia delle Entrate | Schema changes require XML generation updates. Low risk: schema is stable. |

## 7. Acceptance Criteria Summary

The following table maps each module to its primary acceptance test. Detailed acceptance criteria are defined per user story in Section 2. The system is considered "accepted" when all Must-priority requirements pass their acceptance tests and at least 80% of Should-priority requirements pass.

| Module | Acceptance Test | Validation Method |
|--------|----------------|-------------------|
| AUTH | Tradesperson registers, verifies email, logs in, and accesses a protected endpoint. | Automated integration test |
| JOB | Tradesperson creates a job and advances it through all 5 stages. Timestamps are recorded correctly. | Automated integration test + user validation |
| QUOTE | A natural-language description produces an itemised PDF quote with correct totals within 15 seconds. | Accuracy benchmark against 10 manually prepared quotes |
| PHOTO | Photo uploads to S3 with metadata stored in DynamoDB. AI description is generated and editable. | Manual test + user validation |
| OCR | Receipt photo is processed by Textract. Extracted items match the receipt content with >80% accuracy. | Automated test with sample receipts |
| INV | Generated *FatturaPA* XML passes SDI schema validation. | XML schema validation tool |
| DASH | Dashboard displays accurate revenue, completion rate, and overdue invoices for test data. | Automated test with seeded data |
| NOTIFY | Overdue invoice triggers email reminder via EventBridge + SES. | Automated integration test |
